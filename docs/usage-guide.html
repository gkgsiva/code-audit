legacy-audit: usage guide

This guide takes you from a fresh laptop to a finished audit report. You don't need to be a programmer. Every step says what to click, what to type and what you should see.

It covers two ways of working: Windows (the project is in a normal Windows folder) and WSL2 (the project is inside Linux on Windows, in a folder like /home/you/code-audit). Pick yours below to hide the steps for the other. Purple boxes marked 🐧 are WSL2 steps.

Show steps for:

1. What this tool does

Your team is moving old ("legacy") applications to a modern platform: Java 25, Spring Boot 4, Angular 21, PostgreSQL and Google Cloud. Before anyone can plan that move, someone has to answer questions like these:

  • How big is the application? How many lines of code, in which languages?
  • How many web services, screens, database queries, batch jobs and connections to other systems does it have?
  • Which parts are simple and which are complicated?
  • Which database queries will move to PostgreSQL easily, and which need a person to rewrite them?
  • Which third-party libraries are out of date or have known security holes?
  • Roughly how much work will the migration take?

legacy-audit answers these by reading the application's source code and counting. It works with Java (Struts, Spring), C and C++, Pro*C, COBOL, JCL, shell scripts, Autosys job files, IBM MQ and CFT.

What you get at the end

Technical report

A website on your laptop with every count, list and finding. Each number links to the exact file and line it came from.

Management deck

A slide show in the browser for managers: size, risks, readiness and effort. You can print it to PDF.

PowerPoint file

The same slides as an editable .pptx on your company template (Blue, Orange or Purple), with real charts you can change.

Data files

Spreadsheet-friendly CSV files (open in Excel) and other formats for anyone who wants the raw lists.

Three promises the tool keeps

  • It never changes your code. It only reads it. Results go into a separate folder called audit-output.
  • It works offline. Nothing is sent over the internet while it scans, except when OSV-Scanner is installed: by default it asks the free osv.dev service about the libraries found, sending only their names and versions, never your code. Set offline: true to stop that (Vulnerability checks). The reports open without internet too.
  • Every number is counted, not guessed. A program counts; it does not use AI. AI (GitHub Copilot) is an optional extra step that adds written explanations, and the tool checks that the AI didn't change any number.

2. Before you start

Tick these off. Most will already be done.

  • A Windows 10 or 11 laptop where you can install programs (or ask IT to install them for you).
  • Visual Studio Code (VS Code) is installed on Windows.
  • The code-audit project is already on your laptop (it was "cloned" from GitHub) and you can open it in VS Code.
  • An internet connection for the one-time setup (about 5 minutes). After that, no internet is needed.
  • The source code of the application you want to audit, in a folder on your laptop (or a network drive you can reach).
  • WSL2 only: WSL2 with a Linux distribution (usually Ubuntu) is set up, the project was cloned inside it, and you can open the Ubuntu app from the Start menu.
  • WSL2 only: the WSL extension (by Microsoft) is installed in VS Code. To check: Extensions view (Ctrl+Shift+X), search WSL.

Optional extras. You can add these later. The tool tells you what each one adds and works without them.

  • Node.js (version 18 or newer) with Mermaid CLI: only to put diagram pictures inside the PowerPoint file. The PowerPoint itself works without it.
  • OWASP Dependency-Check or OSV-Scanner: to look up known security problems in libraries. Your admin may give you their reports instead. How to install them: Vulnerability checks.
  • GitHub Copilot in VS Code, or an API key for another AI model (OpenAI, Azure OpenAI, Claude, Gemini) or Ollama on your laptop: for the optional AI explanations (section 13).

On WSL2, Node.js and these scanners are installed inside Linux, not on Windows.

WSL2 (Windows Subsystem for Linux) runs a real Linux, usually Ubuntu, inside Windows. If you cloned code-audit inside WSL2, everything in this guide works. Where your files live

  • Linux files (fast for the tool): your Linux home folder, /home/you, written ~ for short. Keep code-audit, your audit folders and, ideally, the application's code here.
  • Seeing Linux files from Windows: in File Explorer, type \\wsl.localhost\Ubuntu\home\you in the address bar (older Windows: \\wsl$\Ubuntu\home\you). Linux also appears at the bottom of File Explorer's left panel.
  • Windows files from Linux: your C: drive is /mnt/c. For example C:\Users\you\Downloads is /mnt/c/Users/you/Downloads. The tool can read code there, but scans are noticeably slower, so copy or clone big applications into Linux.

Replace you with your Linux user name and Ubuntu with your distribution's name if it differs. To see your user name, type whoami in the terminal.

3. Three VS Code basics you will use

You only need three things from VS Code. Learn them once and the rest of this guide is easy.

a. Running a "task" (this is how you'll do almost everything)

The project comes with ready-made buttons called tasks. A task runs a command for you, so you don't have to type it.

  1. At the top of the VS Code window, click the Terminal menu. (If you don't see the menu bar, press Alt once.)
  2. Click Run Task.... A list drops down from the top of the window.
  3. The project's tasks all start with audit: and a number, for example audit: 1. set up (venv + install). Click the one you want. You can also type a few letters, such as audit 4, to filter the list.
  4. If VS Code then asks "Select for which kind of errors and warnings to scan the task output", click Continue without scanning the task output.
  5. Some tasks ask a question, such as which sample to use. Pick an answer from the list and press Enter.
  6. A panel opens at the bottom of the window and shows the task's messages. When it says "Terminal will be reused by tasks, press any key to close it", the task has finished.

Shortcut. Ctrl+Shift+P opens the Command Palette. Type Tasks: Run Task and press Enter for the same list.

On WSL2. Tasks work the same, but only in a WSL window (bottom-left corner says WSL: Ubuntu; see section 5). VS Code then runs the Linux version of each task. In a plain Windows window the tasks fail with errors about .venv\Scripts.

b. The terminal (only for a couple of steps)

The terminal is a window where you type a command and press Enter.

  • Open it: Terminal > New Terminal, or press Ctrl+` (the key under Esc).
  • It opens in the project folder, so the commands in this guide work as written.
  • To paste a command, copy it from this guide (each grey box has a Copy button) and right-click inside the terminal, or press Ctrl+V.
  • To stop something that keeps running (like the app in section 9), click inside the terminal and press Ctrl+C.

On Windows the terminal is PowerShell.

On WSL2. In a WSL window the terminal is bash, a Linux terminal. The line starts with something like you@laptop:~/code-audit$. Commands that need administrator rights start with sudo and ask for your Ubuntu password (the one you chose when you set up WSL, not your Windows password). Nothing appears while you type it; that's normal.

c. Opening a file

The Explorer on the left (the top icon, two sheets of paper, or Ctrl+Shift+E) shows the project's files and folders. Click a folder to open it and a file to view it.

To open a file in Windows (for example a report in your browser), right-click it and choose Reveal in File Explorer, then double-click it there.

On WSL2. Reveal in File Explorer isn't offered in a WSL window. Instead, in the terminal, go to the file's folder and open it in Windows File Explorer, then double-click the file there:

cd docs
explorer.exe .

4. Check or install Python (once)

The tool is written in Python, so Python must be installed. You need version 3.11 or newer.

Windows: first check whether you already have it

  1. Open a terminal in VS Code (Terminal > New Terminal).
  2. Type this and press Enter: 
    python --version
  3. If you see Python 3.11, 3.12, 3.13 or higher, skip to section 5. If you see an older number, an error, or the Microsoft Store opens, carry on below.

Windows: install it

  1. In your browser go to python.org, click Downloads and download the latest Windows installer (64-bit) for Python 3.13 (or 3.12). If your company has a software portal (Company Portal, Software Center), you can install Python from there instead.
  2. Double-click the downloaded file.
  3. Important: on the first screen, tick the box Add python.exe to PATH at the bottom. Without it, VS Code can't find Python.
  4. Click Install Now and wait until it says Setup was successful. Click Close.
  5. Close VS Code completely and open it again, so it notices the new Python.
  6. Open a terminal and run python --version again. It should now show the new version.

The Microsoft Store opens when I type python. Windows has a shortcut that sends python to the Store. Open Windows Settings > Apps > Advanced app settings > App execution aliases, switch off the two entries named App Installer python.exe and python3.exe, then close and reopen VS Code.

On WSL2: use the python3 that Ubuntu already has. Don't install Python on Windows; the tool runs inside Linux. In Linux the command is python3.

  1. Open a terminal in a WSL window (Terminal > New Terminal), or open the Ubuntu app.
  2. Check the version: 
    python3 --version
  3. 3.11 or newer (Ubuntu 24.04 has 3.12): good. Also check that Python can create the tool's private area (the "venv"): 
    python3 -m ensurepip --version
    If that prints a pip version, you're done: go to section 5. If it says No module named ensurepip or ensurepip is disabled, install the missing helper once (it asks for your Ubuntu password): 
    sudo apt update
sudo apt install -y python3-venv
  4. 3.10 or older (Ubuntu 22.04 and earlier): the tool needs a newer Python. Install 3.12 next to it, without touching the old one: 
    sudo apt update
sudo apt install -y software-properties-common
sudo add-apt-repository -y ppa:deadsnakes/ppa
sudo apt install -y python3.12 python3.12-venv
    You then use python3.12 instead of python3 in section 6.
On a Mac or Linux (without WSL)

Mac: install Python 3.12 or 3.13 from python.org (the macOS installer), or with Homebrew: brew install python@3.13. Linux: use your package manager, for example sudo apt install python3 python3-venv. The command is python3: check with python3 --version. The rest is the same as the WSL2 boxes, without the Windows parts.

5. Open the project folder in VS Code (once)

  1. In VS Code click File > Open Folder... and choose the code-audit folder you cloned (for example C:\Users\you\code-audit). Click Select Folder.
  2. VS Code asks "Do you trust the authors of the files in this folder?". Click Yes, I trust the authors. Tasks don't run in a folder that isn't trusted.
  3. A message in the bottom-right corner offers recommended extensions (Python, Python Debugger, Ruff, SQLite Viewer). Click Install. If you missed it: open the Extensions view (Ctrl+Shift+X), type @recommended and install the ones listed under Workspace Recommendations.

On WSL2: open it in a WSL window.

  1. Open the project in one of two ways:
    • In the Ubuntu app, type cd ~/code-audit and press Enter, then code . and Enter. (If you cloned it elsewhere, use that folder.)
    • Or in VS Code press F1, type WSL: Open Folder in WSL..., and pick the code-audit folder.
  2. Check the bottom-left corner of VS Code. It must say WSL: Ubuntu (or your distribution's name). If it doesn't, close the window and try again; in a plain window the tasks fail.
  3. Trust the folder when asked (Yes, I trust the authors).
  4. When VS Code offers the recommended extensions, install them. In a WSL window the button says Install in WSL: Ubuntu; that is the right one. If you missed it: Extensions view, type @recommended, and click Install in WSL: Ubuntu on each.

Next time, File > Open Recent lists it as code-audit [WSL: Ubuntu].

Why these extensions? Python lets VS Code run the tool. SQLite Viewer lets you open the results database by clicking it. The other two are for developers; they do no harm.

6. Install the tool (once)

This step creates a private Python area for the tool inside the project folder (a folder named .venv, the "virtual environment") and installs everything the tool needs into it. Nothing else on your laptop is changed.

  1. Click Terminal > Run Task... and choose audit: 1. set up (venv + install).
  2. Wait. It downloads and installs packages, which takes 1 to 5 minutes. Lines scroll past in the panel at the bottom.
  3. It's done when the last lines say Successfully installed ... followed by a long list of names, and then Terminal will be reused by tasks.
  4. Tell VS Code to use this Python: press Ctrl+Shift+P, type Python: Select Interpreter, press Enter, and pick the entry that mentions .venv (it often says Recommended).
  5. Close any terminals you have open (the bin icon on the terminal panel), so the next one you open uses the new Python.

On WSL2. Use the same task. On Linux and WSL2 it runs python3, the Python Ubuntu already has, so nothing else is needed. In step 4 the .venv entry shows as ./.venv/bin/python.

If you installed python3.12 in section 4 (Ubuntu 22.04 or older), don't use the task. Run this once in the WSL terminal instead, from the code-audit folder, then do steps 4 and 5:

python3.12 -m venv .venv && .venv/bin/python -m pip install -e ".[dev]"

It failed with a network or proxy error. Your company network may block downloads from the Python package site (PyPI). Ask your admin for the offline install described in docs/admin-guide.md > Offline install, or try again on a network that allows it.

It says "python is not recognized". Python isn't installed or wasn't added to PATH. Go back to section 4, and remember to restart VS Code after installing.

WSL2: it says "ensurepip is not available" or "requires a different Python". The first means the venv helper is missing: sudo apt install -y python3-venv, then delete the half-made folder with rm -rf .venv and run the task again. The second means Ubuntu's Python is older than 3.11: follow the 3.10-or-older step in section 4.

9. Audit your own application

For a real application you use the app (also called the GUI): a set of web pages on your laptop where you fill in a form and press buttons. You only type one command, to start it.

Step 1: make a folder for the audit

Each application gets its own audit folder (the "workspace"). It holds the settings, extra inputs and results for that application. Keep it outside the code-audit project.

  1. In Windows File Explorer, create a folder, for example C:\Audits\billing. Use a short path without special characters; spaces are fine.
  2. Decide where the application's code is. You have two choices:
    • Leave it where it is (for example C:\Users\you\git\billing or a network drive). You'll type that path in the form in step 3. The tool only reads it.
    • Or copy it into a subfolder of the audit folder, for example C:\Audits\billing\code.

On WSL2: make the folder in Linux.

  1. In the WSL terminal, type: 
    mkdir -p ~/audits/billing
  2. Decide where the application's code is:
    • Already in Linux (for example ~/git/billing, cloned in WSL): leave it there. Best choice.
    • On the Windows drive (for example C:\Users\you\git\billing): either use it as /mnt/c/Users/you/git/billing (works, but slower), or copy it into Linux once: 
      cp -r /mnt/c/Users/you/git/billing ~/audits/billing/code

Step 2: start the app

  1. In VS Code (with the code-audit folder open), open a terminal: Terminal > New Terminal.
  2. Paste this command, change the folder at the end to your audit folder, and press Enter. Keep the quotation marks. 
    .venv\Scripts\legacy-audit serve --workspace "C:\Audits\billing"
  3. The terminal prints legacy-audit GUI for C:\Audits\billing at http://127.0.0.1:8765/ (Ctrl+C to stop) and your browser opens the app. If the browser doesn't open, copy that address into it yourself.
  4. Leave the terminal running while you use the app. Closing it stops the app.

On WSL2.

  1. In the WSL window (with code-audit open), open a terminal: Terminal > New Terminal.
  2. Paste this command, change the folder at the end to your audit folder, and press Enter: 
    .venv/bin/legacy-audit serve --workspace ~/audits/billing
  3. The terminal prints legacy-audit GUI for /home/you/audits/billing at http://127.0.0.1:8765/ (Ctrl+C to stop). If no browser opens, hold Ctrl and click that address in the terminal, or type http://localhost:8765 into your Windows browser.
  4. Leave the terminal running while you use the app. Closing it stops the app.
On a Mac or Linux (without WSL)
.venv/bin/legacy-audit serve --workspace "/Users/you/Audits/billing"

Next time. To come back to the same application later, run the same command again. Your settings and all earlier runs are still in the audit folder.

Step 3: set it up and run it

On a brand-new folder the app opens on 1. Project setup. The next section walks through every screen; the short version is:

  1. 1. Project setup: type the Application name and click Create audit.yaml. In the form that appears, under Folders, replace the . with where the code is, one folder per line. For example C:\Users\you\git\billing, or code if you copied it into the audit folder. 🐧 WSL2: use Linux paths, for example /home/you/git/billing, /mnt/c/Users/you/git/billing, or code if you copied it into the audit folder. Never C:\.... Click Save audit.yaml.
  2. 2. Inputs: add any extra exports you have (schedules, MQ, database scripts). Skip it if you have none.
  3. 3. Components: untick folders you don't want counted (for example test or old backup folders), then Save choices.
  4. 4. Run: click Re-run and wait for the bar to finish.
  5. 5. Dashboard: your headline numbers.
  6. 8. Reports: click Build all, then Open next to each report.

How long does a scan take? Small applications take seconds. On a typical 4-core laptop, about 2 million lines of code take 3 to 4 minutes the first time. 10. The nine screens of the app

The menu across the top of the app has nine numbered screens. Work through them from left to right the first time. The Theme button switches between light and dark.

On WSL2. The app runs in Linux and you use it from your Windows browser. Everything on these screens works the same, with three exceptions, each explained under its screen: Linux paths in Folders, the Open ... folder buttons, and the Open in VS Code links.

1. Project setup

On a new audit folder this screen shows only an Application name box and a Create audit.yaml button. Type the name (for example Customer billing) and click the button. This creates the settings file (audit.yaml), a corrections file (audit-overrides.yaml), the audit-inputs folders and the Copilot files. You do this once per application. The full form then appears:

  • Application name and Description: shown on every report.
  • Source: choose Local folders (the usual choice) or Git repositories.
  • Folders (for local folders): where the code is, one per line. A path can be full or relative to the audit folder (code). The starting value . means "the audit folder itself"; replace it if your code is elsewhere. Full Windows path example: C:\Users\you\git\billing.
  • Repositories (for Git, optional): one line per repository in the form address | branch | sub-folders | name of an environment variable. The environment variable holds a read-only access token; the token itself is never typed into the tool or saved. Ask your admin if you need this.
  • Target stack: Java, Spring Boot, Angular, database and cloud you are moving to. The defaults match the programme's targets; leave them unless told otherwise.
  • Include and Exclude: which files to read, one pattern per line. The default reads everything except build output and tool folders. To skip a folder, add a line like old-backup/** under Exclude.
  • Save audit.yaml saves the form. Comments and settings the form doesn't show are kept.
  • Advanced: edit audit.yaml as text is for people who know the settings file. Check and save refuses a file with mistakes instead of saving it.
  • Tools on this computer shows the same table as the doctor task in section 7.

On WSL2. In Folders, type Linux paths: /home/you/git/billing, or /mnt/c/Users/you/git/billing for code on the Windows drive. A Windows path such as C:\... won't be found. For Git sources, the environment variable must be set in the Linux terminal that starts the app (for example export GIT_TOKEN=..., typed just before the serve command), not in Windows.

3. Components

A component is one part of the application, such as a web module or a batch module. The tool finds them by itself and shows the list here before you scan:

  • Every folder with a build or project file (pom.xml, build.xml, Makefile, an Eclipse .project, …) is a component.
  • Without build files, the tool looks at the folder names. Folders such as src, WebContent, java, ksh, scripts, properties, conf or sql are parts of the application around them, not components of their own. So a Struts web module keeps its Java and its JSP pages together, and a batch module keeps its Java, its ksh scripts and its properties together.
  • A folder that only holds other applications (for example apps/) is not a component itself: each application inside it is.
  • A folder of shared settings next to the applications (for example config/ or properties/) becomes a config component.

The Type column gives the main kind of each component. When a component holds several kinds of work (for example a web module that also has a nightly batch), the reports list the others under Also holds, and Made of says how many Java, screen, script and configuration files it has.

Shown as three numbers of person-days: low, likely and high. It multiplies the items found by a number of days per item and complexity. It is always labelled "estimate — weights from config", because the days per item are set by the team, not measured. Treat it as a starting point for planning.

Vulnerability checks: OWASP Dependency-Check and OSV-Scanner (optional)

The Libraries and Security pages can show which third-party libraries have known security problems (CVEs). legacy-audit doesn't look these up itself. It reads the results of one of two free scanners. You need only one of them.

Quickest start: OSV-Scanner in online mode. Download one file (about 30 MB) and tell legacy-audit where it is. New audit.yaml files already have offline: false, so there is nothing else to download: during the scan it asks the free osv.dev service about the libraries it finds, in a few seconds. Only library names and versions are sent, never your code. Steps: Option 1. Dependency-Check is optional; add it later if you want a second opinion.

Good atOld applications full of .jar files, and build files (Maven, Gradle)Build files (Maven, Gradle, npm and more) and .jar files
NeedsJava 11 or newer, and a free NVD API key to download its databaseNothing; it's a single program file

How legacy-audit uses them

  • Online or offline. With offline: false, OSV-Scanner asks osv.dev during the scan (needs internet, always up to date, nothing to download first). This is the setting in a new audit.yaml. With offline: true, the scanners never go on the internet during a scan: they use a database you downloaded beforehand and refresh yourself, for example once a week. Dependency-Check always uses its own downloaded database.
  • It finds the scanner through the path you put in audit.yaml, or, if that is empty, on your PATH. Project setup > Tools on this computer (the doctor) then shows it as ok.
  • Reports print the database date, so readers can see how fresh the data is.
  • If neither scanner is installed and no reports are supplied, the reports show a coverage gap ("dependency-check: missing"), and part 5 of the summary report shows a yellow box. That means "not checked", not "no vulnerabilities". With only one scanner, the reports name the other as "not used"; that is fine.

No install at all: use reports from your security team. If another team already runs Dependency-Check or OSV-Scanner (for example in a build pipeline), ask them for the JSON report and add it on 2. Inputs > Vulnerability reports (it goes into audit-inputs/security/). Any file name ending in .json works; the tool recognises which scanner made it. When a report from a scanner is there, that scanner is not run for this application.

Option 1 (quickest): OSV-Scanner in online mode

legacy-audit needs OSV-Scanner version 2 or newer (the current version). Your computer must reach osv.dev during the scan; if your company network blocks it, use Option 2.

Windows

  1. Download it. In your browser go to github.com/google/osv-scanner/releases and, under the newest release, download only osv-scanner_windows_amd64.exe (one file, about 30 MB). You don't need the other files.
  2. Put it in place. Create the folder C:\Tools\osv-scanner, move the file there and rename it to osv-scanner.exe. If Windows or your antivirus blocks it, ask IT to allow it.
  3. Check the version. In a terminal: 
    C:\Tools\osv-scanner\osv-scanner.exe --version
    The first line should say osv-scanner version: 2. followed by more numbers.
  4. Set it up in legacy-audit. In the app, open 1. Project setup > Advanced: edit audit.yaml as text. Find the security: part and change these lines (use forward slashes in the path): 
    security:
  dependency_check:
    enabled: false        # optional: turn on later if you install it
  osv_scanner:
    enabled: true
    path: "C:/Tools/osv-scanner/osv-scanner.exe"
    offline: false        # already set in new audit.yaml files: ask osv.dev, no database to download

  6. Re-run the scan, then build the summary report. Part 5, Dependency vulnerabilities, says "Checked with OSV-Scanner" and lists the problems found, worst first.

18. Questions people ask

Does the tool send our code anywhere?

No. The scan, the app and the reports work entirely on your laptop with no internet. The only times it uses the network are when you explicitly ask it to download code from Git, and during the one-time setup. The optional Copilot step sends the questions you type to GitHub Copilot, under your company's Copilot agreement.

Can it break or change our application?

No. It only reads the source files. Results go into audit-output in the audit folder.

What about passwords in the code?

Passwords and secrets found in configuration files are replaced by **** in every report, data file and in the app's code viewer.

How accurate are the numbers?

They are counted by rules written down in the Appendix of every report ("counting rules"), and every item links to the file and line it came from, so anyone can check. Code that is put together while the program runs can hide some details; the tool rebuilds what it can and marks what it can't. The effort figure is an estimate based on the team's weights.

Do I have to fill in all the inputs?

No. Start with just the code. Add inputs as they arrive and re-run. Missing inputs are listed in every report so readers know.

Can I go back to an older run?

Yes. Every run is kept under audit-output/runs. In the app, use the run selector on Dashboard, Explorer or Reports, or Compare runs.

Can two people use the same audit folder?

The app is for one person on their own laptop, and only one scan runs at a time per folder. To share results, send the report folder or the data pack ZIP.

How do I get a newer version of the tool?

In VS Code (the WSL window on WSL2), use the Source Control view (Ctrl+Shift+G) > ... menu > Pull to update the code-audit folder, or type git pull in its terminal. Then run task 1 again. Your audit folders are not touched. Use Full rescan on the next run.

Can I delete old runs or the cache?

Yes. Each run folder under audit-output/runs can be deleted; cache can be deleted too (the next scan just reads everything again).

Should I use Windows or WSL2?

Either works and gives the same numbers. Use whichever already holds the code: if your team develops in WSL2, keep everything in WSL2; if the code is on Windows, the Windows steps are simpler. Avoid mixing, such as the tool in WSL2 reading big code bases on /mnt/c, which is slow.

19. Glossary

Audit folder (workspace)
The folder for one application's audit: settings, inputs and results.
audit.yaml
The settings file for an audit: application name, where the code is, what to include, target versions. Written by the Project setup screen.
audit-overrides.yaml
Corrections to what the tool detected (folders to leave out, component types). Applied again on every run.
bash
The Linux terminal you type commands into on WSL2.
Batch job
A program that runs on a schedule or in the background, without a user (Autosys jobs, JCL, cron, Spring Batch). When no scheduler file is provided, each batch component counts as one batch, however many ksh scripts it has.
Cache
Saved results from earlier runs, so files that haven't changed don't have to be read again.
Component
One part of the application, such as a web module, a batch module or a shared configuration folder; usually one build file or one application folder (with its src, WebContent, scripts and properties inside).
Coverage gap
An input or tool that was missing for a run. It means "not checked", not "nothing found".
CRUD matrix
A table showing which component Creates, Reads, Updates or Deletes each database table.
CSV
A simple table file that Excel opens.
CVE / vulnerability
A publicly known security problem in a library, with an id like CVE-2021-44228.
DDL
Database scripts that create tables, views and procedures.
Dynamic SQL
A database query that the program assembles from pieces while it runs, instead of writing it out in full. The tool rebuilds it where it can.
Enrichment / stage
The written analysis Copilot adds, in parts called stages (overview, architecture, flows, risks, plan, functional view, component documentation and so on).
NVD API key
A free personal code from the US National Vulnerability Database that lets Dependency-Check download its database quickly. Keep it private.
EOL (end of life)
A library or product version that its makers no longer support or patch.
Evidence
The file and line number a number or item came from. Every count has it.
Finding
An issue a rule found in the code, with a severity (critical, high, medium, low, info).
GUI / the app
The web pages on your laptop, started with legacy-audit serve, where you set up, run and view audits.
Home folder (~)
Your own folder in Linux, /home/you. ~ is short for it.
Integration
A connection to another system: message queue, file transfer, web service call, email and so on.
latest
The folder that always points to the newest run.
Legacy application
An older application that is being moved to the new platform.
Library
Third-party code the application uses, for example a .jar file.
/mnt/c
On WSL2, the Linux name for your Windows C: drive.
PostgreSQL grade
How easily a SQL statement converts to PostgreSQL: auto, review or manual.
Re-run / Full rescan
Re-run reads only new or changed files; Full rescan reads everything again.
Run
One scan, saved in its own folder named by date and time.
SBOM
Software bill of materials: the list of all libraries and versions, in a standard format (CycloneDX) other tools can read.
Screen
A page or form a user sees (a JSP page, a mainframe map).
Service
An entry point that users or other systems call: a web service, servlet, Struts action, CICS transaction and so on.
Stale
An enrichment stage written before the latest scan changed its inputs; it should be redone.
sudo
On Linux, runs a command with administrator rights. It asks for your Linux password.
Task (VS Code)
A ready-made command you start from Terminal > Run Task....
Terminal
The panel where you type commands. PowerShell on Windows, bash on WSL2.
Virtual environment (.venv)
A private Python area inside the project folder that holds the tool, so it doesn't affect anything else on the laptop.
WSL2 / WSL window
Windows Subsystem for Linux: a real Linux inside Windows. A WSL window is a VS Code window connected to it (bottom-left corner says WSL: Ubuntu).

Part of the code-audit project (docs/usage-guide.html). More detailed guides in the same folder: user-guide.md (the app, screen by screen), admin-guide.md (installing for a team, offline install, vulnerability databases, branding), rules.md (changing rules), copilot-agent.md (Copilot for analysts) and validate-in-vscode.md (checking each feature from VS Code).
